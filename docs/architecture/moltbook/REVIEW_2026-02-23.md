## 2. Confirmed Bugs

### BUG-1: `_resolve_moltbook_context()` uses non-existent dict keys

**File:** `plugins/moltbook/plugin_main.py:762-763`
**Severity:** Medium (context display broken, not data flow)

```python
stats = self._content_queue.stats
pending = stats.get("pending", 0)   # KEY DOES NOT EXIST
sent = stats.get("sent", 0)        # KEY DOES NOT EXIST
```

`ContentQueue.stats` returns: `{"queued", "total_enqueued", "total_drained", "total_dropped", "max_size"}`
Result: Queue state is NEVER displayed in context. Always 0.

Also: Line 768 references `self._last_feed_topics` which is never set anywhere in the class.

### BUG-2: `_drain_content_queue()` creates throwaway MoltbookService instances

**File:** `plugins/moltbook/plugin_main.py:664`
**Severity:** Medium (operation logs lost, unnecessary allocations)

```python
def _drain_content_queue(self) -> None:
    service = MoltbookService(self._client)  # NEW instance every drain cycle
```

But `_register_service()` (line 360-366) already creates a singleton registered in ServiceRegistry.
The drain method should use that same instance. Instead:
- Operation logs written to the throwaway instance are lost
- New instance created every heartbeat (every 16 ticks)
- The registered singleton's `_operation_log` stays empty

### BUG-3: Logger says "v2", class is v3

**File:** `plugins/moltbook/plugin_main.py:738`
**Severity:** Low (cosmetic)

```python
logger.info("Content proposer: ResonanceProposer v2 (engine-wired)")
```
Class docstring and module header both say "v3".

### BUG-4: `_last_feed_topics` referenced but never assigned

**File:** `plugins/moltbook/plugin_main.py:768`
**Severity:** Low (dead code path)

```python
if hasattr(self, "_last_feed_topics") and self._last_feed_topics:
    parts.append(f"Feed topics: {', '.join(self._last_feed_topics[:5])}")
```
`_last_feed_topics` is never set anywhere. `_analyze_feed()` doesn't populate it.
This condition is always False.

### BUG-5: STRATEGY.md falsely claims MoltbookResolver was removed

**File:** `docs/architecture/moltbook/STRATEGY.md:489`
**Severity:** Low (documentation error)

Claims: "Dead code cleanup: removed stale MoltbookResolver/boot_moltbook/.pyc ghosts"
Reality: `services/moltbook_resolver.py` (347 LOC) exists with full implementation.
It has 0 production callers — it's prepared infrastructure, not removed.

## 3. Architectural Debts

### DEBT-1: `analyze_feed()` not in ContentProposalProtocol ABC

**File:** `protocols/moltbook_content.py` (ContentProposalProtocol)
**Used at:** `plugins/moltbook/plugin_main.py:626-629`

The plugin does:
```python
if not hasattr(self._proposer, "analyze_feed"):
    return
scored = self._proposer.analyze_feed(unseen)
```

But `ContentProposalProtocol` does NOT declare `analyze_feed()` as abstract.
`EchoContentProposer` also doesn't implement it. This means:
- If someone swaps in a different `ContentProposalProtocol` impl, feed analysis silently disappears
- The `hasattr()` check is a duck-typing workaround, not a protocol contract
- This breaks the stated rule: "Implementations decide WHAT. Plugin decides WHEN."

### DEBT-2: MoltbookResolver is a parallel, dormant system

**File:** `services/moltbook_resolver.py`
**Also:** `plugins/moltbook/plugin_main.py`

Two independent systems exist for the same purpose:
1. **Plugin** (active): `_on_mahamantra_tick()` → heartbeat → drain queue
2. **Resolver** (dormant): `boot_moltbook()` → MantraKernel intent routing

Both create their own `MoltbookClient`. Both register their own listener.
If both activated simultaneously: double API calls, double heartbeats.

Currently safe (resolver has 0 callers). But confusing for future developers.
ARCHITECTURE.md doesn't mention the resolver at all.

## 4. Things the Prior Agent Got Right

These are NOT bugs — verified correct:

### Integrity normalization is correct
`mantra_vm.py:272` already normalizes: `membrane_integrity / P.COSMIC_FRAME`.
The proposer's `_integrity(result) >= 0.5` threshold works correctly against the
VM result dict. CLAUDE.md's note "int 0–21600" refers to the raw cell field,
not the dict output.

### No dual heartbeat conflict
`on_pulse()` exists but is never called by PranaOrchestrator (`_act()` checks for
`plugin.pulse()`, `plugin.execute()`, or callable — NOT `plugin.on_pulse()`).
Only `_on_mahamantra_tick()` fires. No double execution.

### Gateway is functional
`get_gateway()` in `gateway/mahamantra_gateway.py` exists and works.
The 5-gate Pancha Tattva pipeline is wired. Inbound DMs route correctly.

### ServiceRegistry path works for cartridge + tool
Both `cartridge_main.py` and `content_tool.py` try ServiceRegistry first,
fall back to creating a new proposer. Normal boot path shares one instance.
Fallback only fires if plugin fails to boot.

### All 10 infrastructure dependencies exist
LanguageEngine, PromptRegistry, LLMProvider, KnowledgeResolver, ServiceRegistry,
SECTION_SIGNATURES, _GUARDIAN_CONFIGS, render(), mahamantra exports, agent_city
registration — all verified present with correct signatures.

| `follow()` | `follow_agent()` | Yes |
| `subscribe()` | `subscribe_submolt()` | Yes |
| `unfollow()` | `unfollow_agent()` | Yes |
| `unsubscribe()` | `unsubscribe_submolt()` | Yes |
| `get_conversations()` | `get_dm_conversations()` | Yes |
| `get_messages()` | `get_dm_messages()` | Yes |

MoltbookService bridges these correctly. But 8 name mismatches is high.

## 7. Circuit + Prompts Assessment

**`moltbook_content.yaml` circuit:** Well-structured 4-state machine
(SHABDA → ARTHA → PRATYAYA → KARMA). But this is a SPECIFICATION, not executed code.
No circuit executor consumes this YAML in production. It documents intent.

**`config/prompts/moltbook.yaml`:** Context-only templates. No instructions.
This is correct design. The templates fill slots with data from EngineResult,
guardian config, and knowledge resolver. LLM gets dense context.

**`moltbook_intelligence.py`:** Research script that calls private methods
(`_run_pipeline`, `_generate`). Acceptable for research — imports are clear
about what they're doing.
